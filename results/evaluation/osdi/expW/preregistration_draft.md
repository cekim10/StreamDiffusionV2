## 1. Question

M1 rests on one premise: *a small execution-critical state (2.67 MiB) is enough to resume generation at once, and the
stream returns to the uninterrupted one after the late-arriving Sink binds.* Does this hold across inputs, and how often
does the Sink change (an adaptive promotion) inside a restoration window, which is the scope limit of M2/M3's
single-version restoration? W separates three things that Experiment D measured on one workload:
1. **TTFO stability** - execution resumes as fast regardless of the input (a property of the immediate state's size);
2. **visual rejoin** - whether and when the output returns to the reference after bind (a property of the content and of
   the Sink's refresh history);
3. **Sink-version stability** - how often promotions change the Sink, without any migration, separated into changes
   caused by the harness's clip repetition and changes within a clip.

### 3.1 Loop semantics (audited from the code, 2026-10-18)

- **Feeding** (`tools/proto_handoff.build_runtime`, `tools/state_ablation.Runner`): the clip is loaded once
  (`load_mp4_as_tensor`, resized to 480x832) and repeated end-to-end with `video.repeat` (a **hard cut**: the last frame
  of a pass is followed by the first frame of the clip). The session starts from frames 0-4 (`first` = 5); call c
  receives frames [5 + 4c, 9 + 4c) of the repeated tensor. The same arithmetic holds in every run, reference and W1 run
  of a unit, so a given call sees the same input everywhere.
- **Cut call** = a call whose input chunk contains a repeated-tensor frame f > 0 with f mod T = 0. With 4 frames per
  call the cut may fall inside the chunk (e.g. T = 32, call 30 receives clip frames 29, 30, 31, 0). The output at call c
  is the decode of input chunk c - 1 (k = 2 Stream-Batch lag), so a cut reaches the output one call later.
- **Boundary-adjacent calls** = a cut call and the 2 calls after it (the window fixed on 2026-10-17 in
  `../expT/sink_stability_plan.md`). Every other call is **within-clip**. A within-clip call is **first-pass** if all its
  input frames lie in the clip's first pass (frame index < T), otherwise **repeated-input**.
- **Consequences (from `loop_audit.md`):**

| group | loop period | cut calls | W1 calls 30-329 within-clip / adjacent | within-clip windows of w = 6 / 25 / 52 calls | at M = 30: trigger is a cut call? |
|---|---|---|---|---|---|
| LOVEU 32-frame (11) | 8 calls | 6, 14, 22, 30, 38, ... | 186 / 114 | 0 / 0 / 0 | **yes** |
| LOVEU 128-frame (5) | 32 calls | 30, 62, 94, ... | 270 / 30 | 210 / 36 / 0 | **yes** |
| dog | 20.25 calls | 19, 39, 59, ... | 255 / 45 | 160 / 0 / 0 | no (cut at 39 before bind) |
| train | 16.25 calls | 15, 31, 47, ... | 243 / 57 | 130 / 0 / 0 | no (2 cuts before bind) |
| bird / boxing | 63.5 / 62.75 calls | 62, 125, ... / 61, 124, ... | 285 / 15 | 249 / 149 / 34 and 249 / 145 / 31 | no |

  So (i) at the ExpD trigger M = 30, **every LOVEU clip receives a cut in the first post-migration call**; (ii) no
  within-clip window of the restoration length (w = 25) exists for the 32-frame clips, dog or train, and only bird and
  boxing have within-clip windows of w = 52; (iii) the first-pass calls are 0-5 (32-frame), 0-14 (train), 0-18 (dog),
  0-29 (128-frame), 0-61 / 0-60 (bird / boxing): every LOVEU first pass ends before the trigger.

## 4. W1 - Sink-version stability (uninterrupted, no migration)

- One run per unit: the unmodified pipeline for calls 0-329 on one GPU (the reference path, no OTTER transfer), fed as
  in section 3.1.
- Logged per call: sink-slot positions (existing); a content fingerprint of each sink slot per layer on the **value**
  cache (not rotated by RoPE, so a t_refresh realignment does not change it); eviction-queue insertions that target a
  sink slot; the call class (cut / boundary-adjacent / first-pass within-clip / repeated-input within-clip).
- **Promotion** = a change of any layer's sink-slot value fingerprint between consecutive calls, counted from call 1 on
  (the session's first batch and call 0 fill the 3 sink slots; filling is not a promotion). A **version change** = a
  call with at least one promotion (any change invalidates the transferred Sink's digest).
- **Promotions by cause** (each reported with its numerator and denominator, per unit and per group):
  1. *cut-induced*: version changes at boundary-adjacent calls; also the **boundary promotion probability** = share of
     cut calls followed by >= 1 version change within their adjacency window (calls 30-329);
  2. *within-clip, first pass*: version changes per 100 first-pass within-clip calls (calls 1 .. end of first pass; the
     only calls on genuinely new input; few for short clips, reported with counts, no rate below 10 calls);
  3. *within-clip, repeated input*: version changes per 100 repeated-input within-clip calls in 30-329.
- **P_w** for w = 6 (native rejoin-ready ~3.1 s), 25 (1 Gbps T_ref 14.05 s / 0.556 s) and 52 (bind after the final
  move of a rho = 2 schedule), the windows fixed on 2026-10-17, two ways:
  - **as fed**: share of trigger calls c in [30, 330 - w] with a version change in [c, c + w] (what the harness's
    runs experience, cuts included);
  - **within-clip**: the same over windows containing no boundary-adjacent call; computed only where >= 10 such windows
    exist (`loop_audit.md`), otherwise reported "not measurable" (all 32-frame clips, dog and train at w = 25 and 52; the
    128-frame clips at w = 52).
- **Scope classification (rule, not a hypothesis):** a unit is *single-version stable at w* if P_w <= 0.05 (judgment
  value), stated separately for as-fed and within-clip P_w. The as-fed classification interprets the W, R and N runs on
  this harness; the within-clip classification (where measurable) is the scope statement about a stream that does not
  repeat. The dog units' as-fed P_w decides R's rho <= 1 cells (`../expR/preregistration_draft.md` section 7).

## 5. W2 - single migration across workloads

- Scenario A shape: one move A -> B at the trigger call M (**decision D1, section 12**; ExpD used 30), warm
  destination, 1 Gbps, the ExpD harness.
- Policies: **OTTER event-driven** (`reuse_dyn`; a single move with no holders, so M1 + Sink restoration) and **Cold
  restart** (`cold`; fresh caches, no Sink) as the control that tells whether a workload's 35 dB rejoin needs the Sink.
- **Fixed observation horizon:** every run generates at B through call M + 99 (100 post-migration calls, ~56 s; ~74
  calls after a ~26-call bind at 1 Gbps), whether or not it rejoins. Nodes run with `post_chunks` >= 100 (130 planned),
  so the reference covers calls 0 .. M + 129.
- One run per (unit, policy) = 80 runs. Seeds are the replication; timing is summarized per workload over its two seeds.

### 5.1 Reference trajectory and alignment (audited from the code, 2026-10-18)

- **Reference** = the destination node's own uninterrupted session, run at node start (`GpuRuntime.baseline`):
  `Runner.start()` then calls 0 .. M + post_chunks - 1, same seed, same per-call noise seed (`seed x 100003 + c + 1`),
  same repeated input tensor, same GPU model; the decoded uint8 frames of every call are kept (`base[c]`) and cached per
  configuration (`results/evaluation/_reference_cache`, used by cold-started nodes).
- **Run**: the source runs calls 0 .. M - 1 from `Runner.start()`, serializes the Sink at the trigger, and hands off;
  the destination continues at the source's next call index c0 (= M when the move is issued at the trigger; c0 is
  recorded per run). Call indices are absolute in both trajectories, so call c of the run is compared with call c of the
  reference: same input chunk, same noise seed, same Stream-Batch lag (output at c = input chunk c - 1 in both).
- **Comparison** at each destination call c with an output: PSNR = mean over the chunk's 4 output frames of
  10 log10(1 / MSE) on RGB in [0, 1] at 480x832 (99 dB if identical); SSIM on the chunk's last frame only. Both
  trajectories are in the same stretched 480x832 output space, so the aspect transformation does not affect alignment.
  Calls without an output (none for OTTER; the restart call of Cold restart) have no PSNR and never count as >= 35 dB.
- **Rejoin** = the first call >= the first bound call with PSNR >= 35 dB (ExpD definition).
- **Reference Sink changes during restoration (new, from the code):** B's adaptive refresh is frozen until the Sink
  binds, and the transferred Sink is the trigger-time version. If the *reference* promotes between c0 and B's bind call,
  the reference continues on a Sink that B can never bind, so B's output cannot return to the reference except by later
  convergence. Each W2 OTTER run is therefore classified from the reference's per-call value fingerprints (logged in the
  node baseline; W1's run of the same unit as a cross-check): **RVC** (reference version change in [c0, bind call]),
  split into *cut-induced* (all such changes at boundary-adjacent calls) and *within-clip*; otherwise **no RVC**. The
  classification uses the reference only, never OTTER's output. How W-H2 uses it is **decision D2** (section 12).

## 6. Metrics

| metric | definition | role |
|---|---|---|
| TTFO | trigger -> first chunk at B | W-H1 |
| service time | per-call model call + synchronize at B (the nodes' `service_s`), median per run | W-H1 normalizer |
| rejoin calls | calls from the first bound chunk to the first chunk >= 35 dB (section 5.1); **right-censored** at call M + 99 if never reached | W-H2, KM |
| rejoin delay | wall-clock counterpart of rejoin calls (censored likewise) | descriptive |
| sustained rejoin | first call from which >= 35 dB holds for 10 consecutive calls (censored likewise) | descriptive |
| Cold reaches 35 dB | any Cold-restart chunk >= 35 dB in calls M .. M + 99 | W-H3 |
| continuity coverage | share of chunks in M .. M + 99 at >= 35 dB | descriptive |
| RVC class | section 5.1 | stratifier (D2) |
| promotions after bind | value fingerprints at B after bind and in the reference at the same calls | descriptive |

## 7. Confirmatory hypotheses (decision rules fixed at the freeze)

- **W-H1 (TTFO stability).** For every workload, the median TTFO over its two OTTER runs <= 1.0 s, **and** the spread
  (max - min) of the 20 workload medians <= 0.25 x the median service time over all OTTER runs.
  Origins: 1.0 s is G1's bound (frozen 2026-10-16, before ExpD ran); 0.25 call is a judgment value meaning "no workload
  costs an extra quarter of a generation call", motivated by the mechanism (the immediate state's size does not depend
  on content). Recorded prediction: supported (prior TTFO 0.67-0.72 s on three clips).
- **W-H2 (rejoin within the horizon).** OTTER rejoins (rejoin calls not censored) in >= 80 % of the units of the set
  chosen in D2. Origin: 80 % is a judgment value for "generally holds"; it is deliberately below 100 % because prior
  evidence already shows workload-dependent healing. Recorded prediction: uncertain (all three prior clips rejoined;
  LOVEU untested; RVC frequency unknown).
- **W-H3 (rejoin depends on the Sink).** Among units in which OTTER rejoins, Cold restart reaches 35 dB within the same
  horizon in <= 20 % (i.e. the 35 dB criterion discriminates Sink restoration from input-driven convergence in >= 80 %).
  Origin: judgment value, symmetric to W-H2. Recorded prediction: supported for dog (prior ~19-20 dB without the Sink);
  unknown elsewhere. Units in which Cold restart reaches 35 dB are listed as *non-discriminating*, and W-H2 is also
  reported over the discriminating units only (descriptive).

A unit lacking a valid run of either policy makes W-H3 not evaluable for that unit; if more than 10 % of a hypothesis's
units are not evaluable, the hypothesis is NOT EVALUABLE. If D2's set has fewer than 20 units, W-H2 is NOT EVALUABLE on
it (reported with N) and the all-unit result is reported.

## 9. Aspect ratio: facts and a minimal sensitivity experiment (W-AR)

**Facts (code, 2026-10-18).** The only video loader used by the harness and by every inference entry point
(`streamv2v/inference_common.load_mp4_as_tensor`) supports `resize_hw` (a per-frame `TF.resize` to an exact H x W),
`max_frames` and normalization; it has **no crop, pad or aspect-preserving option**. The nodes accept `--height` /
`--width`, but the model's token count per frame follows them (`frame_seq_length` = (H/16) x (W/16) in
`models/wan/causal_stream_inference.py`), so another resolution changes the Sink size, the state sizes and the service
time. LOVEU clips (480x480) are therefore stretched horizontally by 1.73x in the primary pipeline; this stays the
primary preprocessing, unchanged.

**W-AR (descriptive; after the primary set; no hypothesis).** Isolate the effect of the stretch on W's two quality
outcomes while keeping every system quantity fixed:
- *Variant input*: for each W-AR video, a center band of the original, 276 rows x 480 columns (rows 102-377; aspect
  1.739 vs the pipeline's 1.733), written as a new lossless H.264 file (qp 0) outside version control by a committed
  script; the original files are not touched. The unchanged loader then scales it uniformly to 480x832 (residual
  vertical scale difference 0.35 %). The resolution, Sink size, state sizes and service time are identical to the
  primary runs; what changes is the geometry (no stretch) and the content (the top and bottom 42 % of each frame are
  removed). The re-encode's fidelity is reported (PSNR of the decoded variant against the cropped original frames).
- *Videos* (rule fixed now, input properties only): within each LOVEU frame-length group, sort the selected videos by
  motion score and take positions floor((j + 0.5) x n / 2), j = 0, 1 (32-frame: n = 11 -> positions 2, 8; 128-frame:
  n = 5 -> positions 1, 3): 4 videos, each with its selected prompt; seed 0.
- *Runs*: W1 (330 calls) and W2 (OTTER event-driven, Cold restart) on the variant: 4 + 8 = 12 runs (~1 h), compared
  with the same 4 units' primary (stretched) runs: promotions by cause, P_w, rejoin calls, sustained rejoin, PSNR
  trajectory. Reported as a paired table, labelled descriptive; never used to change a primary verdict.
- *Not chosen*: letterboxing (pads 352 columns of synthetic constant content into every frame) and running at a square
  resolution (changes the state sizes and timing, so W2's system metrics would not be comparable; the official demo's
  512x512 shows square inputs are an operating point of the pipeline, which is noted as an alternative if a geometry
  study without content loss is wanted).

## 10. Validity and scope

- ExpD run-validity rules apply (`../followup_common.md` section 2). In W2 an owner-side version event before bind cannot
  occur by construction (the source stops generating at the handoff; B's refresh is frozen until bind); promotions after
  bind are the workload's normal behaviour and are counted, not excluded. Reference-side changes are handled by the RVC
  classification (section 5.1), not as invalidity.
- Loop boundaries are a property of the harness, identical in the run and its reference; they are marked and analysed
  (sections 3.1, 4, 8), not removed. The 32-frame clips are mostly repeated input (8-call loop), and their results are
  always also reported as a separate group.
- PSNR against the reference measures continuity with the uninterrupted stream, not generic quality; W makes no
  perceptual-quality claim.

## 12. Decisions needed before the freeze

- **D1 - trigger call M for W2.** (a) M = 30 as in ExpD: every LOVEU clip receives a cut in the first post-migration call,
  so the migration coincides with a scene cut (a confound for both OTTER and the Cold control). (b) **M = 34 for all 20
  workloads (recommended):** for every workload the trigger is neither a cut call nor boundary-adjacent (the nearest
  earlier cut is at 30 for LOVEU, 19 for dog, 31 for train; bird and boxing have none before 61), chosen from the frame
  arithmetic alone. Cuts inside the restoration window remain for short clips (3 for 32-frame, 2 for dog, 1 for train,
  0 for 128-frame, bird, boxing; `loop_audit.md`); no single M avoids them for an 8-call loop.
- **D2 - unit set for W-H2.** (a) all 40 units; (b) units without RVC (inside the single-version scope); (c)
  **units without a cut-induced RVC (recommended)**: excludes only reference Sink changes caused by the harness's clip
  repetition, keeps within-clip changes (a real limitation of single-version restoration) in the test. All three are
  reported whatever is chosen; the RVC frequency is itself a descriptive result.
- **D3 - W-AR variant.** Center-band crop (recommended; holds the system quantities fixed) or square resolution (no
  content loss; system quantities change).

## 13. What the outcomes mean for the paper

- W-H1 supported: "execution resumes within one call regardless of input" can be stated for the tested workloads.
- W-H2 / W-H3: the rejoin claim is stated with its KM distribution, the RVC strata and the share of non-rejoining and
  non-discriminating units; if W-H2 is not supported, the paper states that continuity recovery is workload-dependent
  and names the classes where it fails.
- W1: the scope sentence on single-version restoration is given as measured fractions (P_w as fed and within-clip,
  promotions by cause), not as an assumption; the harness's clip repetition is named as the source of cut-induced changes.
- W-AR: the stretch's effect on rejoin and promotions is reported as a measured sensitivity, or as not measured.
